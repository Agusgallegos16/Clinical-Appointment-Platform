Plan de Implementación: Sistema de Gestión de Turnos Médicos (Microservicios)
¡Excelente elección! Aprender microservicios es un gran desafío y muy valorado en la industria actual. Trabajaremos con la estructura que ya tienes (Pacientes, Turnos y Notificaciones), dejaremos el frontend para más adelante, y utilizaremos SQL Server.

A continuación, detallo el plan técnico actualizado.

IMPORTANT


Preguntas Abiertas
SQL Server (Base de Datos): Para usar SQL Server en tu computadora sin tener que hacer una instalación compleja de Windows, lo más práctico y profesional es usar Docker. Noté que tienes archivos compose.yaml en tus carpetas. ¿Estás de acuerdo en que configure un contenedor de Docker con SQL Server para que todas nuestras bases de datos corran ahí automáticamente?
Comunicación entre Microservicios: Como tenemos 3 servicios separados, necesitarán hablar entre ellos. Por ejemplo, cuando se crea un turno, el Servicio de Turnos necesita avisarle al Servicio de Notificaciones. Para mantenerlo simple al principio, propongo usar Spring Cloud OpenFeign (que permite a un servicio hacer peticiones HTTP a otro de forma fácil). ¿Te parece bien este enfoque?
Cambios Propuestos
1. Configuración Global (Docker Compose)
Usaremos el archivo compose.yaml en la carpeta raíz (SistemaDeGestionDeTurnos) para levantar una instancia de SQL Server 2022.
Crearemos 3 bases de datos dentro de ese servidor (una para cada microservicio: db_pacientes, db_turnos, db_notificaciones).
2. Microservicio: Gestión de Pacientes (servicioDeGesrtionDePacientes)
Responsabilidad: Administrar la información de los pacientes (CRUD).
Base de Datos: Se conectará a db_pacientes en SQL Server usando el driver mssql-jdbc y Spring Data JPA.
Modelo: Paciente (ID, Nombre, Apellido, DNI, Email, Historia Clínica).
Endpoints: GET /api/pacientes, POST /api/pacientes, GET /api/pacientes/{id}.
3. Microservicio: Turnos (servicioDeTurnos)
Responsabilidad: Administrar las citas médicas.
Base de Datos: Se conectará a db_turnos en SQL Server.
Modelo: Turno (ID, Paciente_ID, Fecha, Hora, Estado). Nota: Guardaremos el ID del paciente, no el objeto completo, para mantener la independencia.
Comunicación: Usará OpenFeign para consultar al Servicio de Pacientes y verificar que un paciente exista antes de darle un turno. También llamará al Servicio de Notificaciones para avisar que se creó un turno.
Endpoints: GET /api/turnos, POST /api/turnos, DELETE /api/turnos/{id}.
4. Microservicio: Notificaciones (servicioDeNotificaciones)
Responsabilidad: Recibir solicitudes de envío de notificaciones y procesarlas.
Base de Datos: Se conectará a db_notificaciones en SQL Server (para guardar un registro/historial de notificaciones enviadas).
Modelo: Notificacion (ID, EmailDestino, Mensaje, FechaEnvio, Estado).
Endpoints: POST /api/notificaciones (Recibe la petición, guarda en BD y simula el envío por consola).
5. Frontend (Aplicación Separada)
Quedará para una fase posterior. Se desarrollará como un proyecto independiente (probablemente en otra carpeta o repositorio) usando HTML/CSS/JS que consumirá las APIs de nuestros microservicios.
Plan de Verificación
Pruebas Iniciales (Postman / Navegador)
Al no tener frontend todavía, probaremos nuestros microservicios usando herramientas como Postman o el propio navegador.
Levantaremos SQL Server con Docker (docker-compose up -d).
Iniciaremos los 3 microservicios en puertos diferentes (ej. Pacientes en 8081, Turnos en 8082, Notificaciones en 8083).
Probaremos crear un paciente en el puerto 8081, y luego asignarle un turno en el puerto 8082, verificando que el servicio de Notificaciones (8083) registre el evento.
